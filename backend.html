How the backend works

Strava API, Cloudflare Workers, GitHub Actions, GitHub Pages, and Telegram.

Information Flow

1Garmin, Apple Watch, or the Strava app records a run and syncs it to Strava.
2The participant signs in once through the Cloudflare Worker and grants Strava API access.
3The Worker receives the Strava callback and triggers the GitHub Actions add-participant workflow.
4GitHub Actions stores private refresh tokens in repository secrets, not in the website code.
5The daily workflow fetches Strava runs, builds data/leaderboard.json, sends Telegram, and commits the public JSON.
6GitHub Pages serves the static website, and the browser reads the public JSON to render the dashboard.

What Each Service Does

Strava API is the source of truth for run distance, date, moving time, and activity validation links.

Cloudflare Worker handles one-time signup, OAuth state protection, Strava callback handling, and GitHub workflow dispatch.

GitHub Actions runs the Python scripts, refreshes Strava access tokens, updates team assignments, rebuilds the leaderboard, and posts Telegram updates.

GitHub Pages hosts the static site. It has no backend server and no API secrets in frontend code.

Telegram Bot API sends the daily group update from the same public leaderboard data used by the website.

Workflow Responsibilities

Daily sync

daily_update.yml runs at 15:59 UTC, which is 11:59 pm Singapore time. It fetches Strava runs, rebuilds leaderboard.json, sends Telegram, and commits the public data.

Participant join

add_participant.yml exchanges the one-time Strava authorization code for a refresh token, updates the private config secret, then refreshes the public leaderboard.

Team changes

update_team.yml changes Team A/B assignment in the private config and rebuilds the leaderboard.

Removal

remove_participant.yml removes a participant token from the private config and refreshes the public JSON.

These workflows share a participant-config concurrency lock so signups, removals, team changes, and Strava token refreshes do not overwrite each other.

Secrets And Runtime Config

GitHub repository secrets

STRAVA_CLIENT_ID, STRAVA_CLIENT_SECRET, TELEGRAM_BOT_TOKEN, TELEGRAM_CHAT_ID, PARTICIPANT_CONFIG_JSON, and GH_SECRETS_TOKEN.

Cloudflare Worker secrets

GITHUB_WORKFLOW_TOKEN dispatches GitHub Actions. STATE_SIGNING_SECRET signs OAuth state and join tickets.

Cloudflare Worker variables

STRAVA_CLIENT_ID, CHALLENGE_SITE_URL, GITHUB_OWNER, GITHUB_REPO, GITHUB_REF, and GITHUB_WORKFLOW_ID.

Private participant config

PARTICIPANT_CONFIG_JSON stores display names, Strava athlete IDs, refresh tokens, teams, optional profile image URLs, and manual-activity policy.

Data Contract

scripts/fetch_strava.py reads the private config, refreshes Strava access tokens, fetches paginated athlete activities, keeps only Run activities in the challenge window, and writes a sanitised generated activity file.

scripts/build_leaderboard.py converts that activity file into data/leaderboard.json. The website and Telegram message both read from this same JSON source. 

{
  "challenge": { "name": "2026 Run Challenge", "timezone": "Asia/Singapore" },
  "generated_at": "2026-05-05T13:12:01+08:00",
  "team_summary": { "Team A": {}, "Team B": {} },
  "leaderboard": [],
  "daily_summary": {},
  "validation_summary": {}
}

Privacy And Fairness

The public JSON intentionally keeps only challenge data needed for the leaderboard: names, teams, profile images when available, distances, run counts, dates, moving time, and Strava activity links.

GPS maps, exact start and end locations, coordinates, heart rate, cadence, power, and other sensitive sensor data are not stored or displayed.

Only Strava activities marked as Run within the challenge period count. Manual activities are excluded unless the organiser explicitly allows them.
